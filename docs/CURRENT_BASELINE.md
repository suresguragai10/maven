## 3. What `npm test` actually proves (and does not)

**Both test files are pure calculator/unit-math tests with zero DOM, zero
network, zero Supabase, zero HTML rendering:**

- `test/calc-utils.test.js` (8 tests) — `buildSchedule()`/`computeVat()` from
  `calc-utils.js`: EMI amortization schedule math, VAT add/extract math.
- `test/tax-calc.test.js` (10 tests) — `computeSlabs()` from `tax-calc.js`:
  income-tax slab computation for FY 2082/83 (single/couple/SSF) and FY
  2083/84 (unified schedule).

**`npm test` proves the tax/EMI/VAT arithmetic functions are correct for the
scenarios exercised. It proves nothing about:**
- Public site page generation (`build.js`, `layout.js`, `ui.js`, `data.js`,
  `pages1.js`–`pages7.js`, `blog.js`, `icons.js`, `client.js`'s own DOM/UI
  behavior beyond the two functions above) — **zero tests**.
- Admin CMS (`admin/admin.js`, 1,160 lines) — **zero tests**.
- Staff Work Desk (`staff/staff.js`, 4,932 lines — the single largest and most
  business-critical file in the repo: Client Work compliance workflow, RLS-
  dependent permissions, Firm Work) — **zero tests in the repository**. Every
  verification of this file across its entire build-out was an ad-hoc,
  throwaway, never-committed mock-Supabase-in-headless-Chrome harness built
  fresh per task and deleted afterward — real verification happened, but none
  of it persists as a repeatable regression suite.
- Database/RLS correctness — the only verification method used to date is
  one-off SQL scripts handed to the repo owner to run manually against the
  live Supabase project (e.g. the JWT-impersonation script from the V2
  permission audit) — not an automated, repeatable test.
- Accessibility, SEO output correctness, CSP/security header behavior.

**Do not describe `npm test` as "full regression" or "the test suite" without
qualifying which slice it covers.** This gap is exactly what Handbook Tasks 2
(browser regression foundation) and 3 (database/RLS test harness) exist to close.

## 8. Documentation drift found (recorded, not fixed — out of scope for Task 0)

Six markdown docs exist claiming to describe current behavior:
`HANDOVER-FINAL.md`, `ADMIN-CMS.md`, `CHANGELOG.md`,
`FULL_AUDIT_AND_REQUIREMENTS.md`, `SETUP-CMS.md`, `content/blog/README.md`,
plus `supabase/README.md`. Verified findings, ranked by severity:

1. **`supabase/README.md`'s "What's intentionally not here" section is
   factually wrong.** It states: *"Notifications/reminders — the product
   decision was 'in-app only'... No email/SMS integration, no `notifications`
   table."* A `notifications` table was built and shipped (in-app only, as
   the doc itself predicted, but the doc says it doesn't exist at all). Its
   own "Migration order" table also only lists 11 of the current 16
   migration files — missing `notifications`, `client_attention`,
   `workflow_settings`, `v2_permission_audit`, and `firm_work_data_model`.

2. **`HANDOVER-FINAL.md` never mentions `/staff/` (Maven Work Desk) or
   `/supabase/` anywhere**, despite `staff.js` being the single largest file
   in the repository and the Work Desk representing the majority of recent
   engineering work. The document's own closing line claims *"everything
   needed to understand, edit, or extend the site is in these 16 sections"*
   — that is no longer true.

3. **Migration files are a running log, not a snapshot — reading any single
   migration file gives a wrong picture of current behavior.**
   `20260811090400_work_items.sql` (original) still shows the pre-hardening
   `work_items_update` RLS policy and the original `guard_work_item_update()`
   trigger body; the actual current versions only exist by additionally
   reading `20260815090000_v2_permission_audit.sql` and
   `20260816090000_firm_work_data_model.sql` in order. No single file, and no
   doc, currently states "reconstruct current state by replaying migrations
   in filename order" as an explicit instruction (`supabase/README.md` says
   files are safe to *re-run*, which is different from saying a single file
   is not authoritative on its own).

4. **`HANDOVER-FINAL.md` §2 and §17 contradict each other on hosting.** §2's
   architecture diagram still shows "GitHub Pages ← publishes dist/
   automatically"; §17 (appended later) correctly says the site migrated to
   Cloudflare Workers. §2 was never removed or corrected — a reader stopping
   at §2 gets the wrong architecture.

5. **`HANDOVER-FINAL.md` §8 sends a future developer to the wrong file for
   the single most consequence-sensitive edit in the repo.** It says *"The
   tax slab table in `client.js` (search for `TAX_TABLES`) needs
   updating."* Verified: `client.js`'s `TAX_TABLES` is a runtime object built
   FROM `_calc.taxTables`, which is populated at build time from
   `content/site.yaml`'s `taxTables:` block — the actual editable source.
   Editing `client.js` directly would not survive the next build. Given the
   Master Session Contract's explicit rule that tax/statutory values need an
   owner-approved primary source and versioned tests, sending someone to the
   wrong file for an annual Finance Act update is a real risk, not cosmetic.
   The TDS claim (`pages5.js`) is technically true but incomplete the same
   way — the actual rates live in `site.yaml`'s `calc.tdsTypes`, consumed
   (not defined) by `pages5.js`.

6. **`HANDOVER-FINAL.md` §13 lists two items as still-pending that are
   already done**: "Real logo — currently a text 'M' mark" (the real logo has
   been live everywhere since an earlier session), and the photos/
   testimonials section describes them as "Not yet built" / "planned for
   2-3 months" when the Testimonials page already exists in the generated
   output (`dist/testimonials.html`, currently `noindex` pending real
   content) and most hero photos are already live.

7. **`ADMIN-CMS.md`'s security description of token storage is backwards.**
   It states the "Remember token" checkbox saves the token to
   `localStorage`. Verified in `admin/admin.js` (~line 1076): the token is
   kept in `sessionStorage` only (cleared on tab/browser close); only
   non-sensitive metadata (owner/repo/branch) goes to `localStorage`. Line
   1131 (`localStorage.removeItem('maven_admin_token')`) is a defensive
   cleanup explicitly for "any token saved by older versions of this page" —
   confirming an earlier version really did use `localStorage` as the doc
   describes, and the doc was never updated after the security improvement.
   The actual behavior is safer than documented, but a security document
   being factually wrong about a security control is itself worth recording.

8. **`content/blog/README.md`** says the blog's `noindex` tag lives "in
   `pages4.js` and `build.js`." Verified: `pages4.js` contains no `noindex`
   reference at all; the logic is centralized in `build.js`/`layout.js`/
   `data.js`. Minor, but would send someone to the wrong file.

9. **`CHANGELOG.md` and `FULL_AUDIT_AND_REQUIREMENTS.md` are self-aware,
   dated, point-in-time documents** (both stamped 2026-07-03, and the audit
   doc explicitly opens with "Implementation status... see CHANGELOG.md for

   they don't claim to be current — but `CHANGELOG.md`'s own description of

10. **`SETUP-CMS.md`** is a one-time bootstrap doc from the original

## 9. Top unprotected risk areas (ranked)

1. **`staff/staff.js` (4,932 lines) has zero persisted automated tests.**
   Every prior verification was a disposable, task-scoped harness. A future
   change with no equivalent ad-hoc testing effort could regress Client Work
   compliance logic or Firm Work isolation with nothing catching it before a
   human notices in production.
2. **No RLS/database regression suite.** Permission correctness (the actual
   security boundary for the whole Work Desk) has been verified via one-off,
   manually-run SQL scripts, not an automated, re-runnable test.
3. **No browser-level test tooling at all.** Neither the public site's build
   output nor the two application bundles have any automated UI/E2E check —
   a build that succeeds and passes `npm test` can still ship a broken page.
4. **No `test:syntax` in CI.** A syntax error in any file not touched by
   `npm test` (i.e. almost everything — see §3) currently ships to
   production undetected by the pipeline; only manually running
   `node --check` (or a browser loading the page) would catch it.
5. **Tax/statutory data source-of-truth is undocumented in the one place a
   future editor is most likely to look** (see §8 finding 5) — a real risk
   given the Master Session Contract's explicit concern about financial/
   legal correctness.
6. **`admin/admin.js` (1,160 lines) has zero automated tests**, and is the
   only code path with write access to the public site's content.
