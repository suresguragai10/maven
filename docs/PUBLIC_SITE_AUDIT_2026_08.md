# Public Site Audit — August 2026

Research-only pass over the 18 indexable public pages (`build.js` `pages[]` array) plus the shared modules that generate them (`layout.js`, `ui.js`, `data.js`, `pages1.js`–`pages7.js`, `styles.css`, `client.js`, `build.js`). No files were changed while producing this report. Findings are split into **real bugs/inconsistencies** (something is factually wrong or inconsistent right now) and **matured opinions** (defensible polish, not a defect). Tax/statutory *numbers* are intentionally excluded — those are tracked in `docs/NEXT_STEPS_TRACKER.md` Group 4 / `docs/OWNER_REVIEW.md`.

Method: read every `pages*.js` module directly (not just the audit docs), grepped `styles.css`/`client.js` for the actual motion/timing values, read `build.js`'s CSP block and `client.js`'s form-handling code directly, and cross-checked every claim below against current source rather than trusting a prior doc's prose.

---

## High priority — documentation now contradicts the live code

These aren't bugs in the site itself — the site is fine — but four separate prior audit docs make factual claims about the current codebase that are no longer true. Since two of those docs (`ARCHITECTURE_MAP.md`, `NEXT_STEPS_TRACKER.md`) are the standing references future sessions are told to read first, leaving them stale is a real risk: the next task could re-do work that's already done, or skip work whose premise quietly changed.

1. **`docs/ARCHITECTURE_MAP.md:12` claims capability-chapter consolidation "has not started."** False. `capabilityChapter()` (`ui.js:109-134`) is fully wired into both Home (`pages1.js:199,215,231`) and Services (`pages2.js:24-33`), rendering the three real chapters — Establish & Comply / Run Your Finance Function / Advise & Report Better — with per-variant CSS (`styles.css:864-909`). `docs/DESIGN_SYSTEM.md:59-70` correctly documents this as already "Wired into Home and Services (Tasks 04–05)" — that doc is the trustworthy one; `ARCHITECTURE_MAP.md`'s headline finding #2 needs updating or removing.

2. **`docs/NEXT_STEPS_TRACKER.md:53` (Group 6) — "other pages still use one-photo-per-category" is not accurate either.** Checked every non-Home/Services page directly (`pages2.js` outsourced-accounting/global-outsourcing/packages; `pages7.js` nfrs-ifrs/international-accounting/virtual-cfo/resources; `pages3.js` documents-needed/industries/faq/contact; `pages4.js` useful-links/blog; `pages6.js` team/testimonials/privacy): none of them render a photo-per-service-category grid. They use a single `pageHero()` background photo plus icon-based `.service-card`/`.value-card`/accordion content (confirmed via `grep` — `servicePhotoMeta`/`capabilityChapter` only appear in `pages1.js` and `pages2.js`). There is no old pattern left on these pages to "consolidate" — if a capability-chapter treatment is wanted there, it's a fresh design decision requiring new photography, not a continuation of already-started work. Worth re-scoping this Group 6 item before anyone picks it up, so they don't go looking for a grid that doesn't exist.

3. **`docs/ARCHITECTURE_MAP.md:26` claims "no child-stagger logic exists anywhere."** False. `.reveal-stagger` is fully implemented: `styles.css:676-687` defines `nth-child` transition-delays (70ms/140ms/210ms/280ms/350ms), `client.js:392,405-421` observes `.reveal-stagger` elements the same way as `.reveal`, and it's actively used on the Home hero (`pages1.js:145`, `<div class="reveal-stagger">`). The code's own comment at `client.js:360-362` even attributes this to a specific task. This claim should be corrected or the finding removed.

4. **`docs/SEO_INTENT_MAP.md:66` claims "KPO" is "not currently used anywhere on the site (confirmed by a full-repo search... every `pages*.js`)."** False today: `pages2.js:173` (the `/global-outsourcing` page body copy) reads "...Virtual CFO support builds on that foundation with higher-skill, knowledge-process (KPO) work — turning accounting records into budgets, forecasts..." This isn't a policy problem — the same document's own §4 guidance says KPO usage on `/global-outsourcing` specifically (management-reporting/Virtual CFO framing, not audit/assurance) would be "truthful, defensible" — but the factual "not used anywhere" claim is now wrong and should be updated so a future SEO pass doesn't rely on it.

5. **`docs/BUSINESS_CONTENT_REVIEW.md:73` (Services page, item flagged P2, "owner approval" pending) says "No CTA/link exists directly on any individual service card."** False today: every `serviceEntry()` card (`ui.js:74-89`) already renders its own "Discuss This Service" button (or a deep-link CTA for Outsourced Accounting/NFRS-IFRS via `SERVICE_DEEP_LINKS`, `pages2.js:13-16`) — confirmed live in `services.html` via `serviceChapterSection()` (`pages2.js:24-33`). This P2 item appears to have been implemented as part of the same Task 05 rearchitecture that added `capabilityChapter()`/`serviceEntry()`, but the review doc was never updated to mark it resolved. Recommend closing it rather than routing it to the owner for approval of something already shipped.

## Medium priority — real, current issues

6. **Home and About still duplicate the exact same "proof panel" content.** `pages1.js:160-172` (Home, `about-snapshot` section, eyebrow "About Maven") and `pages1.js:343-357` (About, `about-snapshot` section, eyebrow "Who We Are") both render `data.aboutText` verbatim and the identical `data.aboutFacts` stamp-list in the same `proof-panel` layout. This is the exact duplication `docs/ARCHITECTURE_MAP.md:31` already flagged and it's still unresolved — a visitor who clicks Home → About sees the same paragraph and the same fact list twice, in a near-identical box, on consecutive pages. Fix suggestion: give About's proof panel a distinct angle (e.g. a longer-form "our story" paragraph instead of reusing `aboutText`) or drop the panel from one of the two pages.

7. **Two micro-interactions run at 300ms, doubling the ~150-160ms most other hover/toggle transitions on the site use.** `.accordion-panel` (`styles.css:511`, `max-height 0.3s`) and `.doc-card-tab` (`styles.css:359`, `background-color/color 0.3s`) are noticeably slower than the site's other interactive transitions (buttons/links/nav toggles cluster around 0.15s–0.22s, see `styles.css:145,191,223,417,449,464,509`). `docs/DESIGN_SYSTEM.md`'s own Motion section (lines 80-87) doesn't set a hard millisecond ceiling for micro-interactions, so this isn't a rule violation, just an inconsistency worth a look — the accordion in particular is a frequently-used control (FAQ, Documents Checklist, NFRS/IFRS technical detail) where a snappier ~200ms would likely feel more responsive without changing anything else.

## Low priority — matured opinions / minor polish

8. **Blog post/index card headings skip a level.** `pages4.js:47` (`blogIndex()`) renders each post title as `<h3>` with no preceding `<h2>` on the page (no `sectionHead()` call before the grid) — jumps straight from the page's `<h1>` to `<h3>`. Contrast with `resources.html`/`useful-links.html`, which correctly use `<h2>` for their card titles in the same no-preceding-`sectionHead` situation (`pages7.js:327`, `pages4.js:10`) — Task 26's own documented rule (see comment at `ui.js:283-285`) says heading level should depend on what precedes it, and blog's cards didn't get the same treatment. Low priority because `blog.html` is currently `hidden`/noindexed with zero real posts (confirmed via `test/seo.test.js` `HIDDEN_FILES`) — this only matters once the owner actually publishes blog content per `docs/CONTENT_AUTHORITY_BRIEFS.md`.

9. **Packages section subtitle reads slightly generic/defensive** ("no fixed one-size-fits-all pricing," `content/site.yaml`, surfaced at `pages1.js:254` and `pages2.js` packages page). Already flagged as P3/style-only in `docs/BUSINESS_CONTENT_REVIEW.md` — re-confirmed still accurate, still genuinely optional, not re-litigating it as new.

10. **The "160-240ms micro-interaction band" cited in `ARCHITECTURE_MAP.md:26` doesn't actually trace back to `DESIGN_SYSTEM.md`.** `DESIGN_SYSTEM.md`'s Motion section only says micro-interactions should "remain small enough not to change layout" — no explicit ms range is defined anywhere as an owner-approved standard. Worth knowing this specific number is one auditor's inferred convention, not a written rule, before treating item 7 above as a governance violation rather than a preference.

## Verified in good shape (evidence, not just a clean bill of health)

- **CSP is real and scoped correctly.** `build.js:343-401` defines three distinct CSP blocks (public/admin/staff) with no `'unsafe-inline'` in `script-src` anywhere (scripts are external, content-hashed files — `build.js:42-70`), `object-src 'none'`, and `frame-ancestors 'self'`. `style-src 'unsafe-inline'` is present and explicitly justified in a comment (`build.js:341-342`) as a known, scoped tradeoff for inline `style="..."` attributes, not an oversight.
- **Contact form handles user input safely.** `client.js:431-459`: the visible fallback summary uses `.textContent` (`client.js:453`), never `innerHTML`, for anything containing user-typed text; `mailto:`/`wa.me` fallback links go through `encodeURIComponent` (`client.js:446-451`). The only `innerHTML` writes on the calculators page (`client.js:733-739,806-833`) use exclusively numeric, internally-computed values (tax slab rows, EMI schedule rows) — no raw user text ever reaches `innerHTML`.
- **No secrets in public JS.** Grepped `build.js`, `client.js`, `layout.js`, `data.js`, `ui.js`, all `pages*.js`, `staff/staff.js`, `admin/admin.js` for service-role/secret/password/API-key patterns — every hit was either UI copy (password `<input>` fields, staff-facing labels) or the already-expected anon key. Confirms the Task 10 credential hardening (Supabase Vault) hasn't regressed into a hardcoded value anywhere client-facing.
- **Images are fully alt-texted and none are decorative-by-accident.** Every `capabilityChapter()` image carries a real, specific `alt` from `SERVICE_PHOTO_META` (`ui.js:8-20`); team photos use the member's name as alt (`pages6.js:18`); logo marks correctly use `alt=""` since they sit beside visible brand text (`layout.js:91,175`). All decorative SVG icons default to `aria-hidden="true" focusable="false"` in `icon()` (`icons.js:49`) — nobody has to remember to add that per call site.
- **Focus-visible and keyboard access are handled, not just hoped for.** A global `:focus-visible` rule (`styles.css:119`) plus component-specific rings for mobile submenu toggles, doc-card tabs, and form fields; the desktop nav dropdown and mobile submenu both use real `aria-expanded`/`aria-controls` with `inert` on collapsed content (`layout.js:25,53,57`), matching the WAI-ARIA disclosure pattern rather than CSS-only hover tricks.
- **The reveal/motion system fails open correctly.** `client.js:401-424`: reduced-motion users and any `IntersectionObserver` construction failure both immediately mark content visible rather than risk stuck-invisible content — this is the documented, load-bearing safety property from `DESIGN_SYSTEM.md:85`, and it's implemented exactly as claimed.
- **SEO technical layer is broad and already regression-tested** (`test/seo.test.js`, 20 tests) — canonical URLs, sitemap parity, structured data (`AccountingService`, `BreadcrumbList`, `FAQPage`), OG/Twitter tags, hero-preload coverage, and internal-link/fragment integrity across every indexable page are all already guaranteed by CI-runnable tests, not just manual spot-checks. Nothing in this audit found a gap outside that test's scope worth adding to it.
- **Design tokens match their own documentation exactly.** Spot-checked every value `DESIGN_SYSTEM.md` claims (palette hexes, `--space-*`, `--section-y`/`--section-y-mobile`, radius, shadow tiers) against `styles.css:9-46` — all match verbatim, no drift found here (unlike the architecture/motion claims above).

## Summary

The site's security posture (CSP, form-input handling, no leaked secrets), accessibility fundamentals (alt text, focus-visible, ARIA disclosure patterns, icon handling), and SEO technical layer are all genuinely solid and already backed by either direct code evidence or an existing automated test. The real, actionable work here is narrow: five prior-audit documents have drifted out of sync with code that has since moved on (mostly *good* news — capability chapters, stagger motion, and per-card CTAs all shipped since those docs were written, they just weren't marked done), one real content duplication between Home and About is still open, and one minor timing inconsistency is worth a look. No new security, accessibility, or SEO defect was found.
