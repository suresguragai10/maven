## REGRESSION BOUNDARY: Firm Work isolation

**PASS**, verified empirically (`firm_work_isolation.matrix.js`, 8 checks, all PASS):

- A negative control first confirms the seeded Firm Work row is real and would appear in an unscoped query — ruling out a vacuous "nothing to leak" pass.
- `loadWork()`'s filter shape, all three of Reports' query shapes, and the Firm Work page's own filter were each replayed directly against the harness database. Firm Work appeared **only** in the one query shape that explicitly asks for it (`work_scope = 'firm'`) — the one "explicitly named report" the acceptance criterion allows.
- Client Detail's `.eq('client_id', id)` pattern (no explicit `work_scope` filter) was separately proven safe **by schema constraint, not by convention**: an attempt to insert a `work_scope='firm'` row with a real `client_id` was rejected by `work_items_scope_fields_check` (confirmed both by the actual insert failing and by a direct catalog check that the constraint exists). A Firm Work row can never carry a `client_id`, so this pattern cannot leak Firm Work into client compliance views even if someone forgot to add an explicit filter.
- One reviewed, intentional exception: the staff-deactivation flow's "does this person have open work needing reassignment" check (`staff/staff.js:5298`) queries by `assignee_id` with no `work_scope` filter. This is **not** a compliance counter, statutory overdue count, period total, or client service report — it's an operational safety check that should legitimately include Firm Work (you wouldn't want to deactivate someone with unreassigned Firm Work either). Reviewed and confirmed out of scope for this boundary, not a violation of it.
